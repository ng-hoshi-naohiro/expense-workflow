## 1. システム概要

### 1.1 目的

複数施設を運営する事業体において、一般経費(施設備品購入・出張交通費・採用関連費等)の事前申請から承認までを電子化するワークフローシステムを構築する。過去に導入した別システムが「使いこなせず形骸化」した経緯があるため、PC操作に習熟していない現場社員でも直感的に操作できるUIを最優先とする。

### 1.2 主要機能

| 区分 | 機能 |
|------|------|
| 申請 | 経費申請の作成、添付書類のアップロード(カメラ撮影含む)、OCR連動の自動入力、下書き自動保存、過去申請の複製 |
| 承認 | 通知から最短5〜8秒で完了するワンタップ承認、生体認証(WebAuthn)、申請内容の自動チェック・アラート |
| 進捗管理 | 申請の進捗マップ、承認の滞留状況可視化、未提出リマインダー |
| 分析 | 経営ダッシュボード(施設×カテゴリ×月次)、予算管理・上限アラート |
| 連携 | バクラク(既存・税理士法人指定)、勘定奉行クラウド、LINEWORKS |
| 管理 | 操作履歴の保存(行政の実地指導・会計監査対応)、マスター管理 |

### 1.3 動作環境

| 項目 | 内容 |
|------|------|
| アプリケーション形態 | Webアプリケーション(PWA化を推奨) |
| 想定ブラウザ | iOS Safari(16以降)、Android Chrome、PC(Chrome / Edge / Safari) |
| 主要操作端末 | スマートフォン(申請者・承認者)、PC(経理・管理者) |
| 認証方式 | WebAuthn(FaceID / TouchID / 指紋認証) / パスワード(フォールバック) |
| アイコンライブラリ | Lucide React(全画面で統一使用) |

## 2. 対象ユーザーとロール

| ロール | 主な利用者 | 主な操作 |
|--------|-----------|---------|
| 申請者 | 施設長、本部役職者 | 経費申請の作成・送信、申請履歴の参照 |
| 承認者 | 本部役職者、上位管理者 | 申請の承認・差戻し |
| 経理担当者 | 経理部 | 承認済データの会計連携、月次集計、予算管理 |
| 管理者 | 管理部門 | マスター管理、ユーザー管理、監査ログ参照 |

申請者と承認者は兼任が前提(本部役職者は自身が申請者かつ他の申請の承認者)。

## 3. デザイン仕様

### 3.1 デザインコンセプト

**「業務に誠実な、上品な道具」**

業務システムであり、信頼感・正確性・落ち着きが最優先。ただし無機質ではなく、和洋折衷の上質さを感じさせるトーンを目指す。介護施設運営という事業特性に合う、誠実で控えめな佇まい。

v1.2.0以降は、上記コンセプトを保ちつつ、純白の背景に白いカードがやや強めの影で浮かぶ「現代的な余白」を採用する。動作の合図には鮮やかな緑(--primary)、強調には和の朱(--accent)、完了状態には信頼の紺青(--success)を割り当て、三色が互いに干渉しない明快な配色階層を構築する。

### 3.2 カラーパレット

CSS変数として定義し、ライトテーマで運用する。

| 役割 | 変数名 | カラーコード | 用途 |
|------|--------|------------|------|
| メインダーク | `--ink` | `#0c1830` | 見出し、本文、ヘッダー背景 |
| サブダーク | `--ink-soft` | `#2a3a5a` | 補足テキスト、説明文、線画イラスト |
| ページ背景 | `--bg` | `#ffffff` | ページ全体の背景(純白) |
| 補助ペーパー | `--paper` | `#f6f3ec` | カテゴリカード背景・セクション区切り等の補助用途のみ |
| 補助ペーパー(暖色) | `--paper-warm` | `#ede8db` | 区切りや帯背景等の補助用途のみ |
| アクセント | `--accent` | `#c8472b` | 重要操作、強調、ナンバリング、ボトムナビ中央申請ボタン |
| アクセント(薄) | `--accent-soft` | `#e8835c` | 補助アクセント |
| 罫線 | `--line` | `#d5cdb8` | 区切り線、ボーダー |
| プライマリ | `--primary` | `#24BD7E` | 主要アクションボタン、リンク |
| プライマリ(濃) | `--primary-dark` | `#1a9560` | プライマリホバー、グラデーション |
| 成功 | `--success` | `#1a4480` | 承認完了、正常状態(プライマリ緑との識別性のため紺青を採用) |
| 警告 | `--warning` | `#b85c00` | 滞留、要確認 |
| エラー | `--error` | `#c8472b` | 差戻し、エラー(アクセント色と同系統) |
| 純白 | `--screen` | `#ffffff` | カード、フォーム背景 |
| ライトグレー | `--screen-soft` | `#f4f5f8` | 入力フィールド背景 |

**配色の使い方:**
- ページ背景は `--bg`(純白)を基調とし、コンテンツカードも `--screen`(純白)を載せる構成。両者は同色のため、カードの存在は強めシャドウ(3.5節)と16pxの角丸で表現する
- `--paper` および `--paper-warm` は v1.1.0 までページ全体の背景に使用していたが、v1.2.0 で純白基調に変更したため、補助用途(セクション区切り背景・カテゴリカード背景・帯状の領域強調)のみで使用する
- アクセント色 `--accent` は本当に重要な箇所に限定(多用しない)。ボトムナビゲーション中央の「申請」ボタンの強調には引き続き使用する
- ボタンの主要アクションは `--primary`(緑)を使用
- 「承認済」「完了」状態は `--success`(紺青)を使用。プライマリ緑との同系色衝突を避けるため、色相を大きく離している

### 3.3 タイポグラフィ

Google Fontsから以下の3種類を読み込む。

| 役割 | フォント | ウェイト | 用途 |
|------|---------|---------|------|
| 見出し(明朝) | `Noto Serif JP` | 400, 500, 700 | 大見出し、画面タイトル、印象的な数字 |
| 本文(ゴシック) | `Noto Sans JP` | 300, 400, 500, 700 | 本文、ボタン、入力フィールド |
| 等幅 | `JetBrains Mono` | 400, 500 | メタ情報、ID、タイムスタンプ、金額の桁揃え |

**フォントサイズ最小値:**
- 本文: 16px(PC不慣れ層への配慮、最小でも14px)
- ボタン内テキスト: 16px
- 補足説明: 14px
- メタ情報: 12px
- ボタン高さ: 最低48px(タップしやすさ)

### 3.4 スペーシング

| サイズ | 値 | 用途 |
|--------|-----|------|
| xs | 4px | 細部の調整 |
| s | 8px | 要素内の余白 |
| m | 16px | 一般的な要素間 |
| l | 24px | セクション内の余白 |
| xl | 32px | セクション間 |
| xxl | 48px | 大セクション間 |

### 3.5 角丸とシャドウ

| 用途 | 値 |
|------|-----|
| ボタン | `border-radius: 12px` |
| カード | `border-radius: 16px` |
| 入力フィールド | `border-radius: 12px` |
| カードシャドウ | `0 6px 16px rgba(12, 24, 48, 0.10)` |
| 入力フィールドシャドウ | `0 1px 3px rgba(12, 24, 48, 0.05)` |
| モーダルシャドウ | `0 24px 48px -16px rgba(12, 24, 48, 0.25)` |

**シャドウ階層の原則:**
背景が純白でカードも純白のため、シャドウの強度差で視覚階層を表現する。「カード(強) > 入力フィールド(弱)」の階層を保つこと。

## 4. UI設計原則

PC操作に習熟していないユーザーが申請者となる前提で設計する。

### 4.1 一画面一目的の原則

1つの画面では1つの主要タスクのみを扱う。情報過多を避け、次に何をすればよいかを常に明示する。

### 4.2 アイコン単独使用の禁止

すべての操作要素は「アイコン+テキストラベル」のセットで提示する。アイコンのみのボタンは禁止する。理由: アイコンの意味は学習を要するため、PC不慣れ層には伝わりにくい。

### 4.3 タップ領域の確保

ボタンの最小タップ領域は48px×48px。スマートフォン操作時の誤タップを防止する。

### 4.4 確認ダイアログの徹底

申請送信、承認、差戻し、削除等の不可逆操作の前には必ず確認ダイアログを表示する。「よろしいですか?」ではなく「○○を承認します。よろしいですか?」のように具体的な対象を明示する。

### 4.5 進捗・状態の常時可視化

ユーザーが「今、自分はどの段階にいるのか」を常に把握できるようにする。フォームには「ステップ1/3」のような進捗表示(共通コンポーネント6.11参照)、申請には進捗マップ(共通コンポーネント6.10参照)を設置する。

### 4.6 エラーメッセージは原因と対処を明示

「エラーが発生しました」のような抽象的な表現は禁止。「金額が読み取れませんでした。明るい場所で撮り直してください」のように、原因と次のアクションを必ず伝える。

### 4.7 アクセシビリティ

- カラーコントラスト比はWCAG AA基準(4.5:1以上)を満たす
- 色のみで状態を伝えない(テキストやアイコンを併用)
- フォーカスインジケーターを明確に表示

### 4.8 レスポンシブ対応

- スマートフォン(375px〜): 申請者・承認者の主要動線
- タブレット(768px〜): 補助
- PC(1024px〜): 経理・管理者業務、ダッシュボード

スマホ優先で設計し、PCはレスポンシブ拡張とする(モバイルファースト)。

## 6. 共通コンポーネント仕様

### 6.1 グローバルヘッダー

全画面の最上部に固定配置する。

| 要素 | 内容 |
|------|------|
| ロゴ・サービス名 | 左端、明朝体(Noto Serif JP)で「ワークフロー」と表示 |
| メインナビゲーション | PC: ヘッダー右側に「ホーム」「申請」「承認待ち」「履歴」のテキストリンク |
| 通知ベル | アイコン+未読件数バッジ、タップで通知センター遷移 |
| ユーザーアイコン | 右端、タップで設定メニュー(プロフィール/ログアウト) |
| モバイル時 | ハンバーガーメニュー(左端)+通知ベル+ユーザーアイコン |

ヘッダー背景は `--screen`、下部に `--line` の1px罫線。

### 6.2 ボトムナビゲーション(モバイルのみ)

スマートフォン表示時、画面最下部に固定配置する。

| 項目 | アイコン+ラベル |
|------|----------------|
| ホーム | 家アイコン+「ホーム」 |
| 申請 | プラスアイコン+「申請」(中央、強調表示) |
| 承認 | チェックアイコン+「承認」(未承認件数バッジ) |
| 履歴 | リストアイコン+「履歴」 |
| その他 | メニューアイコン+「その他」 |

中央の「申請」ボタンは円形に強調、`--accent` 色を使用。

### 6.3 ボタン

| 種別 | スタイル | 用途 |
|------|---------|------|
| プライマリ | 背景 `--primary`、白テキスト、`border-radius: 12px` | 主要アクション(申請する、承認する) |
| セカンダリ | 背景 `--screen`、`--ink` テキスト、ボーダー `--line`、`border-radius: 12px` | 補助アクション(戻る、キャンセル) |
| デンジャー | 背景 `--accent`、白テキスト、`border-radius: 12px` | 差戻し、削除 |
| サクセス | 背景 `--success`、白テキスト、`border-radius: 12px` | 完了確定 |

すべてのボタンは最低高さ48px、内側パディング上下12px・左右24px。

### 6.4 入力フィールド

| 要素 | スタイル |
|------|---------|
| 背景 | `--screen-soft` |
| ボーダー | 通常時 `--line`、フォーカス時 `--primary` 2px |
| 角丸 | 12px |
| シャドウ | `0 1px 3px rgba(12, 24, 48, 0.05)`(軽量) |
| ラベル | フィールド上部、ゴシック14px、`--ink-soft` |
| ヘルプテキスト | フィールド下部、12px、`--ink-soft` |
| エラーメッセージ | フィールド下部、12px、`--error` |
| 必須マーク | ラベル末尾に「※必須」をテキスト表示(赤丸アスタリスクは使わない) |

入力フィールドのシャドウは、カードシャドウより明確に弱くすること(視覚階層の保持)。

### 6.5 カード

情報の塊を表現する基本単位。

| 要素 | 値 |
|------|-----|
| 背景 | `--screen`(純白) |
| 角丸 | 16px |
| パディング | 16px〜24px |
| シャドウ | `0 6px 16px rgba(12, 24, 48, 0.10)` |
| ボーダー | なし(シャドウで分離) |

ページ背景も `--bg`(純白)で同色のため、カードの存在感はシャドウと角丸で表現する。

### 6.6 ステータスバッジ

| 状態 | 背景色 | 文字色 | ラベル |
|------|--------|--------|--------|
| 下書き | `#e6e6eb` | `--ink-soft` | 下書き |
| 申請中 | `#fff5e6` | `#b85c00` | 承認待ち |
| 承認済 | `#e7ecf5` | `--success` | 承認済 |
| 差戻し | `#fde8e3` | `--accent` | 差戻し |
| 滞留中 | `#fff5e6` | `#b85c00` | 滞留(3日以上) |

「承認済」の背景色は v1.2.0 で `#e8f4ee`(薄緑)から `#e7ecf5`(薄紺青)に変更した(成功色の変更に伴う派生)。

### 6.7 確認ダイアログ

不可逆操作の直前に表示する共通モーダル。

| 要素 | 内容 |
|------|------|
| 背景オーバーレイ | `rgba(12, 24, 48, 0.5)` |
| ダイアログ | 中央配置、白背景、角丸16px、最大幅400px |
| タイトル | 明朝体18px、対象を具体的に明示 |
| 本文 | ゴシック14px、何が起きるかを説明 |
| ボタン | プライマリ(実行) / セカンダリ(キャンセル)を横並び |

### 6.8 並び替えコントロール

すべての一覧画面・表形式画面で共通利用する並び替えコンポーネント。

#### 6.8.1 動作仕様

| 項目 | 内容 |
|------|------|
| ソート方向 | 各キーで昇順/降順を切替可能(クリック/タップでトグル) |
| デフォルト | 多くの場合「申請日 降順(新しい順)」。画面ごとに既定値を別途指定 |
| 複合ソート | 不要(単一キーソートのみ。要件複雑化を避ける) |
| 状態保持 | 画面遷移して戻った際に直前の並び替え状態を保持 |

#### 6.8.2 UIパターン(2種類を画面特性で使い分ける)

**パターンA: プルダウン式(カードリスト型の一覧で使用)**

| 要素 | 内容 |
|------|------|
| 配置 | 一覧上部右側 |
| 表示 | 「並び替え: 申請日(新しい順) ▼」 |
| プルダウン項目 | ソートキー一覧(画面ごとに定義) |
| 昇降切替 | プルダウンの右に上下矢印アイコン+テキスト「昇順/降順」、タップでトグル |

**パターンB: 列ヘッダ式(表形式の画面で使用)**

| 要素 | 内容 |
|------|------|
| 配置 | テーブルの列ヘッダ |
| 操作 | ソート可能列のヘッダをクリックで昇順/降順をトグル |
| 視覚表現 | アクティブ列のヘッダに上向き/下向き矢印アイコン+テキスト「昇順/降順」を併記(アイコン単独使用は禁止: UI設計原則4.2) |
| 非ソート列 | 矢印なし。ヘッダ自体は通常のテーブルヘッダ表示 |

どちらのパターンも、現在の並び替え状態がテキストで明示されること(「申請日(新しい順)」のように)が必須要件。

### 6.9 空状態の表現

データが0件のとき(申請履歴0件、承認待ち0件、通知0件、検索ヒット0件等)に表示する共通コンポーネント。

#### 6.9.1 構成要素

| 要素 | 内容 |
|------|------|
| カラーイラスト | 中央配置、横幅約160〜240px |
| 短文メッセージ | 明朝体16〜18px、状況を端的に説明(例: 「まだ申請がありません」) |
| 補足説明 | ゴシック14px、`--ink-soft`、次の行動を示唆(例: 「ホームから新しい申請を作成できます」) |
| CTAボタン | プライマリボタン、状況に応じた次のアクションへ誘導(例: 「申請を作成する」) |

#### 6.9.2 イラストの制約

空状態のイラストは「親しみやすさ」と「業務システムの品格」を両立させるため、以下の制約を必ず守ること。

| 観点 | 規定 |
|------|------|
| 配色 | 本案件のパレット内で完結すること(`--primary` `--accent` `--success` `--ink` `--ink-soft` のみを使用) |
| スタイル | フラット幾何 or 細線+部分塗り。厚塗り・グラデーション過剰・写実表現は禁止 |
| 構図 | 構図はシンプル。複雑な背景・複数の人物・装飾的な小物の多用は避ける |
| 表情 | 人物を描く場合は表情を控えめに。子供っぽい誇張は避ける |

#### 6.9.3 適用画面の例

| 画面 | 空状態のメッセージ例 |
|------|------------------|
| SC-06 申請履歴一覧 | 「まだ申請がありません」+「申請を作成する」CTA |
| SC-08 承認待ち一覧 | 「承認待ちの案件はありません」+「ホームに戻る」CTA |
| SC-10 通知センター | 「新しい通知はありません」+「ホームに戻る」CTA |
| SC-13 監査ログ | 「該当する操作履歴はありません」+「検索条件を変更」CTA |

### 6.10 進捗マップ(申請プロセス可視化)

申請の進行状況を「申請→1次承認→2次承認→完了」のステップで可視化する共通コンポーネント。SC-03ホーム画面の「進行中の申請」ミニ表示、SC-07申請詳細画面のメイン進捗表示、SC-09承認詳細画面のヘッダー部分などで使用する。

#### 6.10.1 レスポンシブ仕様

ビューポート幅に応じて表示形式を切り替える。

| ブレークポイント | 表示形式 | 理由 |
|----------------|---------|------|
| 〜767px(スマホ) | **縦タイムライン** | 各ステップに「氏名・役職・処理日時・滞留日数」をゆとりを持って表示できる |
| 768px〜(タブレット縦持ち以上・PC) | **横並びステップインジケーター** | 全工程を一目で俯瞰でき、ダッシュボード的に把握できる |

タブレット横持ち時はビューポート幅で768px以上となるため、横並び表示となる。

#### 6.10.2 横並び形式(PC/タブレット)

```
[申請]----[1次承認]----[2次承認]----[完了]
  済        進行中         待機         待機
 5/7      5/7 14:23                       
                ↓
            田中部長
            (滞留 2日)
```

進行中ステップは `--accent` でハイライト、滞留3日以上は警告アイコン+「滞留 ○日」表示。完了ステップは `--success`(紺青)のチェックマーク。

#### 6.10.3 縦タイムライン形式(スマホ)

```
●────────────
│  申請
│  佐藤 美咲(青葉ヶ丘ホーム施設長)
│  2026/05/07 09:32
│  済
│
●────────────
│  1次承認
│  田中 健一(本部 経理部長)
│  2026/05/07 14:23 受付
│  進行中(滞留 2日)
│
○────────────
│  2次承認
│  待機
│
○────────────
   完了
   待機
```

各ステップの円(●/○)はステータスを表す:
- ● 塗りつぶし `--success`(紺青): 完了済
- ● 塗りつぶし `--accent`(朱): 進行中
- ○ 中抜き `--line`: 待機中

縦線は `--line` の2px、進行済区間は `--success` で濃く描画する。

### 6.11 フォームステップ進捗

複数ステップに分かれるフォーム(SC-05申請フォーム等)で、現在地を示す共通コンポーネント。

#### 6.11.1 構成

ヘッダー直下に配置し、以下を併記する。

| 要素 | 内容 |
|------|------|
| 数字表示 | 「ステップ 1 / 3」(等幅フォントで現在/全体を表示) |
| ステップ名 | 「内容入力」「内容確認」「送信完了」など、現在のステップ名 |
| プログレスバー | 数字表示の下に細い進捗バー(高さ4px)。完了済区間は `--primary`、未完了区間は `--screen-soft` |

数字派の高齢者にも視覚派にも対応するため、数字とプログレスバーの両方を必ず併記する。

#### 6.11.2 例

```
ステップ 1 / 3 : 内容入力
████████░░░░░░░░░░░░░░░  33%
```

完了率は (現在ステップ - 1) / 全体ステップ * 100 で計算するのではなく、現在ステップ / 全体ステップ * 100 で計算する(例: 1/3 なら 33%、2/3 なら 66%、3/3 なら 100%)。これにより、ユーザーは「今いるステップが完了に近づいている」感覚を得られる。

### 6.12 イラストレーション規定

本システムにおけるイラストの採用範囲・スタイル指針。

#### 6.12.1 採用範囲

イラストは以下の画面に限定して採用する(全画面採用はしない)。

| 採用画面 | 用途 |
|---------|------|
| SC-01 ログイン画面 | 上部のヘッダーエリアに配置し、システムへの入り口としての温度感を与える |

それ以外の画面(ホーム、申請フォーム、承認詳細、ダッシュボード等)では、業務システムとしての落ち着きを優先し、イラストを使用しない。

#### 6.12.2 スタイル指針

| 観点 | 規定 |
|------|------|
| 配色 | パレット内のみ(`--primary` `--accent` `--success` `--ink` `--ink-soft`)。それ以外の色は使用禁止 |
| スタイル | フラット幾何 or 細線+部分塗り。厚塗り・グラデーション過剰・写実表現は禁止 |
| キャラクタ | 人物を描く場合は抽象寄り(表情を控えめに、子供っぽい誇張なし) |
| サイズ | 横幅 160〜240px(スマホでも縦に詰まらない範囲) |
| ファイル形式 | SVG(将来的なテーマ変更時の色差し替えを容易にするため) |

### 6.13 アイコン規定

#### 6.13.1 ライブラリ

全画面で **Lucide React** を統一使用する。他のアイコンライブラリ(Heroicons、Phosphor、Material Icons等)との混在は禁止。

#### 6.13.2 使用原則

UI設計原則4.2の通り、すべての操作要素は「アイコン+テキストラベル」のセットで提示する。アイコンのみのボタンは禁止する。

#### 6.13.3 サイズ規定

| 用途 | サイズ |
|------|-------|
| ボタン内 | 18〜20px |
| ナビゲーション | 24px |
| 大型カード(カテゴリ選択カード等) | 40px |
| ステータスインジケーター | 16px |

#### 6.13.4 申請カテゴリのアイコン

申請カテゴリ選択画面(SC-04)で使用する代表アイコンは、Lucide React内から以下を使用する。

| カテゴリ | Lucideアイコン名 | 概念 |

## 7. 画面別詳細仕様

### 7.1 SC-01: ログイン画面

#### 7.1.1 画面の目的

ユーザーが本システムにログインするための入り口。初回はメールアドレス+パスワードで認証し、デバイス登録(SC-02)へ誘導する。2回目以降は登録済みデバイスでの生体認証ログインを優先する。

#### 7.1.2 画面構成

| エリア | 内容 |
|--------|------|
| ヘッダーイラスト | 上部中央、横幅240px程度のSVGイラスト(共通コンポーネント6.12のスタイル指針に従う)。介護施設運営の文脈に合う、柔らかな建物・植物・申請書類等の抽象的モチーフ |
| ロゴ・サービス名 | イラスト直下、明朝体で「ワークフロー」 |
| サブタイトル | 「一般経費承認システム」14px |
| ログインフォーム | 中央配置、最大幅400px |
| 生体認証ボタン | 登録済みデバイスでアクセスした場合に最上部に表示 |
| メールアドレス入力欄 | プレースホルダー「会社のメールアドレス」 |
| パスワード入力欄 | パスワード表示/非表示切替ボタン付き |
| ログインボタン | プライマリボタン、横幅100% |
| 補助リンク | 「パスワードを忘れた方」(小さく下部) |

#### 7.1.3 主要動作

- 生体認証ボタンタップ → WebAuthnのブラウザAPIを呼び出し → OS生体認証ダイアログ → 成功時にホーム画面へ遷移
- メール+パスワード入力 → ログインボタン → サーバ認証 → 初回なら SC-02 へ、2回目以降ならホーム画面へ

#### 7.1.4 デザイン上の留意点

- 背景は `--bg`(純白)

- ヘッダーイラストは過剰な装飾にせず、純白の余白を活かす控えめな配置

#### 7.2.1 画面の目的

初回ログイン時に、現在使用しているデバイスをWebAuthnで「承認端末」として登録する。1回限りの操作で、所要時間は約1分。

#### 7.2.2 画面構成

#### 7.2.3 主要動作

- 登録ボタンタップ → WebAuthn `navigator.credentials.create()` 呼び出し → OSの生体認証ダイアログ → 成功時にホーム画面へ遷移

#### 7.3.1 画面の目的

### 7.5 SC-05: 申請フォーム画面

#### 7.5.1 画面の目的

選択されたカテゴリに応じた申請内容を入力する。本システムの中核画面。

#### 7.5.2 画面構成(共通要素)

| エリア | 内容 |

| カテゴリ別フォーム | 後述 |

下書き保存ボタンを画面右上テキストリンクとした理由: 申請フォームは縦に長く、画面下部のボタンだけでは入力途中で押しにくいため。下端固定の主CTA(「次へ」)とは別に、いつでも保存できる導線を上部に確保する。

**施設備品購入:**

| 購入品目 | テキスト | ※必須 |
| 用途 | テキストエリア | ※必須 |
| 業者名 | テキスト | ※必須 |
| 金額(税込) | 数値(OCRで自動入力) | ※必須 |
| 購入希望日 | 日付選択 | ※必須 |
| 見積書/領収書 | カメラ+ファイル添付 | ※必須 |

**出張交通費精算:**

| 項目 | 入力種別 | 必須 |
|------|---------|------|
| 出張日 | 日付範囲 | ※必須 |
| 出張先 | テキスト | ※必須 |
| 目的 | テキスト | ※必須 |
| 経路・金額 | 行追加可能なリスト | ※必須 |
| 領収書 | カメラ+ファイル添付 | ※必須 |

**採用関連費:**

| 項目 | 入力種別 | 必須 |
|------|---------|------|

#### 7.5.4 カメラ起動と写りチェックのフロー

1. カメラボタンタップ → ブラウザのMediaDevices APIでカメラ起動
2. シャッター → 撮影直後にクライアントサイドでブレ・暗さ・はみ出しを判定
3. 問題があれば「ピンボケしています。撮り直しますか?」と即時表示。「撮り直す」「そのまま使う」を選択
4. OKならサーバへ画像送信 → OCR処理 → 金額・日付・店舗名を抽出 → フォームへ自動入力
5. ユーザーは内容を確認・修正

#### 7.5.5 主要動作

- 「次へ」ボタン → 入力内容のサマリ確認画面(SC-05のステップ2)
- 確認画面で「申請する」ボタン → 確認ダイアログ → 申請送信 → SC-07 申請詳細画面へ
- 「保存」テキストリンクタップ → 即座に下書き保存(画面遷移なし、フィードバックのみ表示)
- 入力中に画面遷移したり通信が切れても、入力内容は10秒ごとに自動保存される

### 7.6 SC-06: 申請履歴一覧画面

#### 7.6.1 画面の目的

#### 7.6.2 画面構成

### 7.9 SC-09: 承認詳細・ワンタップ承認画面

#### 7.9.1 画面の目的

通知から最短5〜8秒で承認を完了させる。WebAuthn生体認証で本人確認+電子署名による監査証跡を実現する。

#### 7.9.2 画面構成

| エリア | 内容 |
|--------|------|
| 承認待ちタグ | 上部に「承認待ち」バッジ |
| 申請タイトル | 大きめのテキストで「○○施設 備品購入」 |
| 金額(強調表示) | 明朝体32px以上で大きく表示「¥12,000」 |
| 申請メタ情報 | 申請者、用途、申請日 |
| 添付書類リンク | 「領収書を見る」(タップで拡大プレビュー) |
| 勘定科目の自動推定 | 自動仕訳の推定結果と信頼度表示「推定: 消耗品費(信頼度 高)」 |
| 自動チェックアラート | 該当する場合は警告バナー |
| アクションボタン | 画面下端固定で「承認する」(プライマリ・大) / 「差戻す」(セカンダリ)を配置 |

#### 7.9.3 ワンタップ承認のフロー

1. 「承認する」ボタンタップ
2. WebAuthn `navigator.credentials.get()` 呼び出し
3. OS生体認証ダイアログ表示(FaceID / 指紋)
4. 認証成功 → 端末内秘密鍵で署名 → サーバへ送信
5. サーバが公開鍵で検証 → 承認確定 → ログ記録
6. 「承認しました」完了画面表示(5〜8秒で完結)
7. 申請者へ自動通知

#### 7.9.4 差戻し時のフロー

1. 「差戻す」ボタンタップ
2. コメント入力モーダル(必須)
3. 確認ダイアログ → 差戻し送信
4. 申請者へ通知

#### 7.9.5 デザイン上の留意点

- 金額は最も目立つ要素として配置(誤承認防止)
- 「承認する」ボタンには微細なパルスアニメーションで視認性を上げる(過剰にしない)
- 添付書類は1タップで全画面プレビュー可能に

### 7.11 SC-11: 経営ダッシュボード画面

#### 7.11.1 画面の目的

#### 7.11.2 画面構成
